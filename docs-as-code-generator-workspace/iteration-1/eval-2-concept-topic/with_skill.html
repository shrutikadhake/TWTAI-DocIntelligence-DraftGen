Custom API Rate Limits in AppScan Enterprise

AppScan Enterprise provides a custom API rate limiting system that allows you to control how many requests your application can handle within a specified time window. This concept topic explains how the rate limiting feature works, how it interacts with system components, and the prerequisites for implementation.

What Are Custom API Rate Limits?

Custom API rate limits are configurable thresholds that restrict the number of API requests your system accepts within a defined time window. When a client exceeds the configured limit, the API returns a 429 Too Many Requests response, preventing further requests until the next window begins.

The rate limiting system protects your AppScan Enterprise deployment by preventing abuse, ensuring fair resource distribution, and maintaining system stability under high request volumes.

How Rate Limiting Works: The Component Interaction Flow

Custom rate limits involve three core components that work together in a specific sequence:

  1. Global Configuration File — The system reads rate limit settings from the YAML configuration file at /etc/scanner/config.yml. This file contains the api_settings block, which controls whether custom rate limiting is enabled globally.
  2. Scanner Daemon — The scanner-daemon process loads the configuration when it starts. The daemon does not support hot-reload, meaning configuration changes require a daemon restart using sudo systemctl restart scanner-daemon.
  3. CLI Interface — The scanner-cli command-line tool applies specific rate limit values to the running daemon using the config update command. CLI commands are rejected if custom limits are not enabled in the global configuration file.

The Prerequisites Flow

Rate limiting requires a specific sequence of prerequisites before custom limits can be applied:

  1. Enable custom limits in the global configuration — Open /etc/scanner/config.yml and set custom_limits_enabled: true within the api_settings block. If this step is skipped, the CLI command returns a 403 Forbidden error with the message "Rate limit configuration is disabled globally."
  2. Restart the daemon — After modifying the YAML file, restart the scanner daemon process so it reads the updated configuration.
  3. Authenticate with admin privileges — CLI commands require authentication using a valid admin token. The token must not be expired.

Key Concepts

Configuration File Structure

The api_settings block in /etc/scanner/config.yml contains the following elements:

api_settings:
  timeout: 30
  custom_limits_enabled: true
  default_limit: 500
  • timeout — The API request timeout in seconds.
  • custom_limits_enabled — Boolean flag that enables or disables the custom rate limiting feature globally. Set to true to allow the CLI to accept rate limit updates.
  • default_limit — The fallback request limit if no custom limit is specified.

CLI Command Syntax

Once custom limits are enabled and the daemon is restarted, you use the CLI to apply specific rate limit values:

scanner-cli config update --api-limit <number> --window <seconds>
  • --api-limit <number> — The maximum number of requests allowed within the time window (e.g., 1000).
  • --window <seconds> — The duration of the time window in seconds (e.g., 60).

A successful update returns 200 OK: Rate limits updated.

Error Responses

Understanding error responses helps you troubleshoot rate limiting configuration:

  • 403 Forbidden — Indicates that custom limits are not enabled in the global configuration file. Enable custom_limits_enabled: true in /etc/scanner/config.yml and restart the daemon.
  • 429 Too Many Requests — Indicates that the API request limit has been exceeded. The client must wait until the next rate limit window begins before sending additional requests.

Interaction Between Components

The three components must be coordinated for rate limiting to function:

  1. The global configuration file (YAML) acts as the gatekeeper. If custom_limits_enabled is false, the CLI rejects all rate limit update attempts.
  2. The scanner daemon enforces the configuration by reading it at startup. Changes to the YAML file require an explicit daemon restart; configuration does not update automatically.
  3. The CLI tool communicates rate limit values to the daemon. Once the daemon accepts the CLI command, it begins enforcing the new limits against incoming API requests.

Validation and Verification

After applying custom rate limits, you can verify that the configuration took effect by sending test requests to the API endpoint. When the request count exceeds the configured limit, subsequent requests receive a 429 Too Many Requests response, confirming that the rate limit is active and enforced.

Summary

Custom API rate limits in AppScan Enterprise protect system resources by controlling request volume. The feature requires enabling a global setting in the YAML configuration file, restarting the daemon to load the updated configuration, and using the CLI tool to set specific limit values. Understanding the interaction between these three components—configuration file, daemon process, and CLI interface—ensures successful rate limit implementation.
