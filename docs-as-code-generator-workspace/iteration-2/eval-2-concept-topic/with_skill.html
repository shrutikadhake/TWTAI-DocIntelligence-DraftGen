Custom API rate limits in AppScan Enterprise

Custom API rate limits allow you to control how many requests the scanner daemon accepts within a specified time window. This concept topic explains how the configuration system, daemon, and CLI work together to enforce these limits.

Overview

AppScan Enterprise uses a three-component system to manage custom API rate limits:

  • A global YAML configuration file that enables the feature
  • A background daemon that enforces the limits
  • A command-line interface (CLI) that applies specific rate limit values

To function properly, all three components must be configured in a specific sequence. If you skip any step or perform them out of order, the daemon returns a 403 Forbidden error.

How the prerequisite flow works

Before you can apply custom rate limits, you must complete a critical prerequisite: enabling the feature in the global configuration file. This is necessary because custom limits are disabled by default for security reasons.

When you run the CLI command to set rate limits without first enabling the feature, the daemon denies the request and returns an error: Error 403: Rate limit configuration is disabled globally.

The prerequisite flow consists of three stages:

  1. Enable the feature in the configuration file. You modify the global YAML file at /etc/scanner/config.yml to set custom_limits_enabled: true under the api_settings block.
  2. Restart the daemon. The daemon does not automatically reload configuration changes. You must restart the service using sudo systemctl restart scanner-daemon to load the updated settings.
  3. Apply the custom limits via CLI. After the daemon restarts, you run the CLI command to set specific rate limit values: scanner-cli config update --api-limit <number> --window <seconds>.

Component interactions

Configuration file. The /etc/scanner/config.yml file contains the master setting that gates access to custom limits. The relevant section looks like this:

api_settings:
  timeout: 30
  custom_limits_enabled: true
  default_limit: 500

When custom_limits_enabled is false, the daemon rejects all CLI requests to modify rate limits.

Daemon. The background service (scanner-daemon) enforces rate limits by tracking incoming requests and rejecting any that exceed the configured threshold. The daemon reads the configuration file only at startup. Configuration changes do not take effect until you explicitly restart the service.

CLI. The scanner-cli tool communicates with the daemon to apply or modify rate limit settings. It accepts two parameters:

  • --api-limit <number> specifies the maximum number of requests allowed.
  • --window <seconds> specifies the time interval (in seconds) over which the limit is measured.

For example, scanner-cli config update --api-limit 1000 --window 60 allows 1,000 requests per 60 seconds (approximately 16 requests per second).

How the system enforces limits

Once you configure a rate limit, the daemon tracks each incoming API request. When a client exceeds the specified limit within the time window, the server responds with an HTTP 429 Too Many Requests status code. This signals to the client that it must back off and retry later.

For example, if you set a limit of 1,000 requests per 60 seconds and a client sends the 1,001st request before 60 seconds have elapsed, the daemon blocks that request and returns a 429 response.

Key design purpose

Custom rate limits serve two primary purposes:

  1. Protect the scanning infrastructure. Rate limits prevent a single client from overwhelming the scanner daemon with excessive requests, which could degrade performance for all users.
  2. Enable fair resource sharing. By enforcing predictable request quotas, the system ensures that multiple clients can reliably use the service without one client monopolizing all available resources.
