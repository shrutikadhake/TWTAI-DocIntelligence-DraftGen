**Role**
Act as an expert Documentation Draft Generator and Senior Technical Writer specializing in Docs-as-Code workflows and DITA-structured content.

**Task**
Process a raw text file containing developer message logs (`v10_12_rate_limit_chat.txt`) and automatically convert it into a clean, well-structured HTML draft for a procedural "Task" topic that explains how to configure custom API rate limits.

**Context**
Our team is preparing for the AppScan Enterprise v10.12.0 general availability release. We need to document a new feature for custom API rate limits. The raw input data is a noisy Slack/Teams chat export containing developer and QA back-and-forth. The log contains the actual procedural steps, prerequisites (e.g., YAML configuration), CLI commands, and troubleshooting details, but they are buried under conversational noise, failed attempts, and irrelevant tangents. We follow the Microsoft Manual of Style (MSTP) for all technical documentation.

**Constraints**

* **Noise Filtering:** Extract only the procedural facts. Ignore all chat noise, timestamps, usernames, timezone discussions, and developer banter.
* **Style Enforcement:** Strictly enforce Microsoft style principles (such as using active voice and second person) before outputting the final HTML. Do not generate the final draft until the content aligns with Microsoft style guidelines.
* **Formatting Rules:** You must enforce the centralized formatting guidelines and style parameters defined in the team's shared `rules.md` file before generating the final HTML.
* **Accuracy:** Ground the procedure strictly in the provided log. Do not hallucinate steps, endpoints, or error codes not present in the text. Ensure code snippets and CLI commands are properly formatted within HTML `<code>` or `<pre>` blocks.
* **Format:** Output strictly as clean HTML5.

**Output**
Produce a single HTML document structured logically as a DITA Task topic. The output must include:

* An `<h1>` Title indicating the task.
* A brief `<p>` introduction explaining the goal.
* An `<h3>` section for Prerequisites, explicitly highlighting the global YAML file modification (`/etc/scanner/config.yml`).
* An `<ol>` containing the step-by-step procedure, including restarting the daemon and executing the CLI commands.
* An `<h3>` section for Expected Results, detailing the successful validation test (e.g., the `429 Too Many Requests` response).
* An `<h3>` section for Troubleshooting, explaining how to resolve the `403 Forbidden` error if prerequisites are missed.
